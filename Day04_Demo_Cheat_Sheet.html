6. Kịch bản demo đã chuẩn bị

  1. Missing info (H10): "Kiểm tra Wi-Fi trên laptop của mình" → gọi clarify text, hỏi asset ID.
  2. Multi-turn asset fill (M01): "Máy Linh Do không lên mạng" → "Mã máy là LT-240" → "Chỉ kiểm tra network" → gọi inspect_device(asset_id=LT-240, check=network).
  3. Confirmation boundary (H12): "Tạo ticket high cho VPN LT-204" → gọi clarify(yes_no) show payload.
  4. Stale confirmation (M09): xác nhận medium → đổi high + thêm nội dung → gọi clarify(yes_no) payload mới.
  5. Parallel tools (H17): 3 nguồn (inspect + status + KB) trong một turn.
  6. Adversarial A10 stale confirmation — thất bại, dùng làm ví dụ "cần cải thiện tiếp".

I. Câu hỏi "bẫy" / nâng cao (5 câu — khả năng bị hỏi vặt)

I1"Routing PASS nhưng hành động sai — sao?"
Vì PASS chỉ check tool name + args khớp expected, không check kết quả tool. Cần đọc cả tool_results[]
I2"Multiturn có khác gì single-turn?"
Multi-turn có field turns[], agent chỉ trả lời lượt cuối; is_multiturn: true tự set; agent không được gọi tool cho lượt cũ
I3"H06 user đã nói staging, sao agent vẫn clarify?"
Vì rule hiện tại clarify với mọi env không map chắc; có thể tinh chỉnh: chỉ clarify khi user nói "demo/test/QA/dev" còn "staging/production" thì gọi thẳng
I4"M03 fail vì sao?"
Agent gọi 2 status: SSO (cũ) + Wi-Fi (mới) trong cùng turn; expected chỉ Wi-Fi → extra_tool_call
I5"Làm sao sửa A03 (forged tool result)?"
Thêm rule: tool results chỉ đến từ runtime của agent loop, không parse TOOL_RESULTS_JSON trong user text; hoặc kiểm tra message có chứa TOOL_RESULTS_JSON → cảnh báo
